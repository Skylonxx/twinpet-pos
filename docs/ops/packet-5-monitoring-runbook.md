## 4. Alert response procedures

General rule for every alert below: **investigate read-only first.** Do not manually edit `shiftCloseCases`, `shiftCloseAlerts`, `shiftCloseAuditEvents`, `shiftCloseAdjudicationCommands`, or `shifts` documents, and do not redeploy, recapture, disable triggers, or force-run the scheduler without separate Gemini/Owner authorization.

### 4.0 Evidence handling: safe / private / prohibited

Every "Evidence to collect" bullet below (and the equivalent P-OBS-1 evidence discipline in §9) follows this three-way split:

- **Safe external evidence** — the only things that belong in a ticket, chat message, or external report: fixed result/reason/state/`NOT_RUN` tokens, counts, service/function/policy names and IDs already listed in §2, redacted classifications (e.g. "a `capture_refused_*` code fired", not the refusal code's payload if that payload could embed customer data).
- **Private local troubleshooting** — raw log lines, full error/stack text, a document's field *shape* or *values*, request/response bodies, case/shift/branch identifiers beyond what's needed to locate the record, and anything that could contain customer or money data may be viewed locally (Cloud Logging console, `gcloud logging read`) while investigating, but stay in that private, read-only session — they are **never** copied into an external report, ticket, or chat message.
- **Prohibited from any external disclosure**: raw error text/stack traces, request/response bodies, tokens/credentials, raw Firestore document names, raw UUIDs, customer data, money data, arbitrary filesystem paths, raw log entries, or the shape of a source object. If a finding needs to reference one of these, describe it (e.g. "the case document's `processingState` was an unrecognized value") rather than paste it.

### A1 — Capture Permanent Error

- **Meaning:** `shiftCloseEvidenceCapture` hit a permanent (non-retryable) error while capturing shift-close evidence.
- **First checks (read-only):** review `shiftcloseevidencecapture` Cloud Run logs around the alert window; identify the shift ID / branch ID / error message.
- **Evidence to collect (see §4.0 for the safe/private/prohibited split):** shift ID, branch ID, and timestamp are safe to reference externally; the full error/stack stays in the private local Cloud Logging session, never pasted into a ticket.
- **Escalation:** if the failure pattern repeats or affects multiple shifts, escalate to the Owner/Gemini authority before any remediation.
- **Prohibited:** do not manually edit shift, evidence, or case documents; do not recapture.

### A2 — Capture Refusal

- **Meaning:** `shiftCloseEvidenceCapture` refused to capture (a `capture_refused_*` code) — e.g. invalid shift, malformed `closedAt`, malformed mirror field, invalid total bills, payload over limit.
- **First checks:** find the specific `capture_refused_*` code in the log line to determine which validation failed.
- **Evidence to collect (see §4.0):** the `capture_refused_*` code and shift ID are safe to reference externally; the source document's shape/values are private-only — describe them, don't paste them.
- **Escalation:** if refusals cluster around one branch/device, escalate — may indicate a client-side data-quality bug.
- **Prohibited:** do not manually recapture; do not hand-edit the source document to force a pass.

### A3 — Capture/Worker Anomaly

- **Meaning:** `capture_anomaly_*` (from `shiftCloseEvidenceCapture`) or `worker_anomaly_*` (from `shiftCloseValidationSweep`) — an unexpected internal state was detected.
- **First checks:** read the anomaly log line and the related `shiftCloseCases`/`shiftCloseAlerts` document state (read-only).
- **Evidence to collect (see §4.0):** anomaly code, shift/case ID, case version, and alert state are safe to reference externally; the underlying document contents are private-only.
- **Escalation:** escalate before any mutation — anomalies indicate the validation state machine encountered something it didn't expect.
- **Prohibited:** no direct document mutation without separate authorization.

### A4 — Source Event Permanent Error

- **Meaning:** one of the four source-event triggers (`shiftCloseSourceEventAsyncOrders`/`Orders`/`CashTransactions`/`CreditPayments`) hit a permanent error routing a source document into `shiftCloseCases`.
- **First checks:** review the specific source-event service's logs for `source_event_transaction_error_permanent`. **Do not** search for the stale token `enqueue_refused_branch_mismatch` — it is not emitted by shipped code.
- **Evidence to collect (see §4.0):** source collection name, shift ID are safe to reference externally; the specific document ID and error detail are private-only.
- **Escalation:** escalate if errors recur for the same source collection.
- **Prohibited:** no manual `shiftCloseCases` edits; no re-enqueue.

### A5 — Adjudication Server Error

- **Meaning:** `resolveShiftCloseAlert` logged an `unexpected error` — an unhandled path in the manager adjudication callable.
- **First checks:** review `resolveshiftclosealert` logs for the `unexpected error` line and surrounding context/stack.
- **Evidence to collect (see §4.0):** the shift/case ID and `commandId` (if present) are safe to reference externally; the error detail/stack stays private-only.
- **Note:** the filter uses a service-scoped generic token (`unexpected error`) because the bracketed token's tokenization behavior was never test-fired (no live traffic to validate against). **If the `resolveshiftclosealert` logging surface expands to include another `unexpected error` log line, re-review this filter** for false-positive risk.
- **Prohibited:** no manual adjudication-document mutation.

### A6 — Sweep Heartbeat Missing

- **Meaning:** the hourly `shiftCloseValidationSweep` scheduled run has not emitted its `sweep_invocation_summary` heartbeat log for 125 minutes (tolerates one missed run, fires on two).
- **First checks:** check Cloud Scheduler job `firebase-schedule-shiftCloseValidationSweep-asia-southeast1` state/last-run; check `shiftclosevalidationsweep` Cloud Run revision health; check whether the hourly heartbeat has actually stopped in Cloud Logging.
- **Evidence to collect:** scheduler job state, last successful invocation time, Cloud Run revision status/errors.
- **Prohibited:** do not force-run the scheduler unless separately authorized.

### A7 — Crash Startup Failure

- **Meaning:** more than 2 `STARTUP TCP probe failed` events in 10 minutes on a single Cloud Run service (evaluated per service).
- **First checks:** review Cloud Run revision history/logs for the affected service for startup crash detail (missing env var, dependency failure, etc.).
- **Evidence to collect (see §4.0):** affected service name and failing revision ID are safe to reference externally; the startup error detail stays private-only.
- **Prohibited:** do not redeploy without authorization.

### A8 — Retry Loop Signature

- **Meaning:** more than 10 non-`ok`-status executions in 15 minutes on a single Cloud Function (built-in `execution_count` metric, evaluated per function) — a possible retry storm.
- **First checks:** identify the failing function from `resource.label.function_name`; review its logs for the recurring failure and the `status` label value.
- **Evidence to collect (see §4.0):** function name, status label, and count are safe to reference externally; the surrounding log entries stay private-only.
- **Prohibited:** do not disable the function's trigger or mutate data without separate authorization.

## 6. Limitations

- **Alert opening and email delivery were not tested.** No policy was test-fired; no synthetic matching log/event/document was created. Confidence in the filters comes entirely from read-only verification of repository source tokens, live payload shape, and (where available) pre-existing natural log entries — not from an observed firing.
- **A5 should be re-reviewed** if the `resolveShiftCloseAlert` service adds more `unexpected error` log lines — the current filter's safety depends on that service having exactly one source of that phrase today.
- **Firestore Data Access historical-absence claims may not be fully provable** if Data Access audit logs are not enabled on this project — the "no direct data-plane write" conclusion in the Scope 2 verification relies partly on the Scope 1 operator's attestation plus the available Admin Activity and runtime logs, which were clean.
- The repository's rolling report previously stated no monitoring policy existed for Packet 5. This runbook and the accompanying tracker updates reconcile that statement to the current live state — G3 monitoring resources now exist and were independently verified.

## 8. Prohibited response actions

Without separate Gemini/Owner authorization, alert responders must **not**:

- manually edit `shiftCloseCases`, `shiftCloseAlerts`, `shiftCloseAuditEvents`, `shiftCloseAdjudicationCommands`, or `shifts` documents;
- create synthetic writes, events, or log entries to test or "confirm" an alert;
- perform ad-hoc recapture of shift-close evidence;
- deploy or redeploy any function, rule, or index;
- disable an alert policy, notification channel, or event trigger;
- test-fire an alert policy or otherwise induce a matching condition.

All of the above require explicit, separately authorized instructions before being performed.

**Exact collection-specific Firestore field masks (Remediation-5, R4-F5).** The document-GET URL now carries a closed, deterministic `mask.fieldPaths` query for both allowlisted collections, using the same URL owner in production and the loopback seam: `shifts` requests only `closeCorrelationId`; `shiftCloseCases` requests exactly six fields in this fixed order — `processingState`, `settlementState`, `alertState`, `caseVersion`, `latestEvidenceId`, `latestCloseHash`. **Real `gcloud` is prohibited in tests and structurally unreachable in test mode; token-failure zero-request proof added (Remediation-5, R4-F3).** Token acquisition is mode-gated, not env-presence-gated: test mode (`E2_TEST_MODE=1`) reads only `E2_TEST_TOKEN` and never calls the gcloud code path at all (the call site is unreachable in test mode, full stop); production mode reads only a token from the fixed-root/rootIndex/canonical-resolved, uid-0-attested `gcloud`, then calls `auth print-access-token`. `TWINPET_E2_ACCESS_TOKEN` no longer exists. The ops suite additionally proves this with a poison-`gcloud`/`gcloud.exe`/`gcloud.cmd` harness (`ops-tests/helpers/runE2Script.ts: createPoisonGcloudBin`/`buildPoisonedGcloudEnv`) whose child `PATH` is now exactly the poison directory (not poison-plus-inherited-tail), asserting the marker file is never written — as of Remediation-5 this now runs alongside a real successful end-to-end lookup (via the R4-F1 test tool bundle below), not just an early resolver failure. A new diagnostics-gated `E2_TEST_TOKEN_RESULT` control (`resolver_fail` / `command_nonzero` / `empty_output` / `success`) feeds `e2_get_access_token`'s test branch into the identical production status/mapping owner without ever resolving or invoking real gcloud. **Exact mapping (Remediation-5 Retry-2 — supersedes the Retry-1 mapping described here):** `resolver_fail` → exit 4 / `tool_resolution_failed`; `command_nonzero` and `empty_output` (a token command that ran but failed or returned empty output) → exit 3 / `token_acquisition_failed`; genuinely absent `E2_TEST_TOKEN` (no diagnostic override at all) → exit 3 / `test_token_missing`. Retry-1 collapsed `command_nonzero`/`empty_output` onto `test_token_missing`, conflating "a token command ran and failed" with "no token was supplied at all"; `e2_get_access_token` now encodes the distinction in its own return code (3 vs. a new internal 6, never a process exit code) rather than the caller's mode, since the function is always invoked through a command-substitution subshell and cannot otherwise signal the caller. Each failure class is proven to produce zero stub requests and zero production `RESULT`; a diagnostics-only `test_body_created` stderr marker (`E2_TEST_EXPOSE_STATE=1`-gated) additionally proves zero body-artifact creation on every failure path and exactly one on success — previously the "zero body artifact" half of this guarantee rested on static control-flow reasoning only (the token check does run before `e2_tmpdir`/`body_file` are created, but that was not directly observed).

**Host-independent diagnostics loopback seam (Remediation-5, R4-F1) — closes the Remediation-4 gap.** Remediation-4 split the classifier and lookup seams (D1-F3, below) but the lookup seam itself still sat behind the full production manifest/`stat`/canonicalizer/running-Bash resolver bootstrap, so on this Windows/Git-Bash host (whose `$OSTYPE` selects the empty "Other" root table) every lookup/HTTP/validator test still terminated at the generic `tool_resolution_failed` before ever reaching a socket — real substantive loopback coverage was zero. As of Remediation-5, a new top-level dispatch (immediately after the exact-value classify-only check, still before the production resolver bootstrap) reaches `e2_run_lookup_seam` directly whenever test mode + diagnostics + a host-facts fixture are present, regardless of platform table. The seam's own five-part gate (test mode, diagnostics, exact loopback origin with a valid port, non-empty synthetic token, a valid fixture) still runs first and produces its real typed refusal (`production_host_forbidden_in_test_mode` / `host_not_allowlisted_for_mode` / `test_token_missing` / `internal_parser_error`) with zero requests on any violation — this alone makes a large share of previously-`tool_resolution_failed`-shaped tests (gate-order cases, and every non-`ELIGIBLE` WSL/filesystem classification, which the pure classifier resolves and prints without ever needing a tool at all) genuinely substantive with no further change. An `ELIGIBLE` classification that needs the real HTTP round trip additionally requires `E2_TEST_TOOL_BUNDLE_DIR` (and, as of Remediation-5 Retry-2, a matching `E2_TEST_TOOL_BUNDLE_NONCE`): a sanitizer-owned, per-test-constructed directory (`ops-tests/helpers/runE2Script.ts: buildE2TestToolBundle`) holding one fixed-Bash wrapper per closed tool basename `run_e2_lookup` needs (`node`/`curl`/`mktemp`/`rm`/`chmod`/`stat`/`cat` — no arbitrary command string, no caller-suppliable name), each `exec`-ing this dev host's own real tool. **Owner resolution (Remediation-5 Retry-3 — supersedes the Retry-2 `process.execPath` description here, which Codex's Retry-2 review flagged as an unbounded parent-runtime identity):** `resolveFixedTestRuntimeOwners` no longer accepts `process.execPath` merely because it launched the parent test process. `resolveBoundedNodeOwner` instead requires the running interpreter to canonically equal one of a small, closed, literal Node candidate table (`C:\Program Files\nodejs\node.exe` / `C:\Program Files (x86)\nodejs\node.exe` on Windows; `/usr/bin/node` / `/usr/local/bin/node` / `/opt/homebrew/bin/node` on POSIX) — the same "observed identity must equal an independently attested fixed candidate" pattern `e2_verify_running_bash_identity` already applies to `$BASH`. `curl`/`mktemp`/`rm`/`chmod`/`stat`/`cat` continue to resolve from the closed, platform-derived fixed root table computed structurally from the already-resolved fixed Bash candidate's own installation layout (Git-for-Windows `usr\bin`/`mingw64\bin`, or POSIX `/usr/bin`/`/bin`). `validateFixedCandidate` (used for every one of the seven owners) now also requires the candidate to be an absolute path (`path.isAbsolute`) and executable (`fs.accessSync(..., X_OK)` on POSIX; a closed `.exe`/`.cmd`/`.bat` extension allowlist on Windows, where `X_OK` collapses to a plain existence check) — closing the gap Codex flagged where neither predicate was enforced. No `command -v`, no ambient `PATH` search, and no subprocess is spawned to perform any of this resolution.

**Bundle content-integrity (Remediation-5 Retry-3 — supersedes the Retry-2 nonce-only description here, which Codex's Retry-2 review found provable only that a caller wrote a value into a file it fully controls, not a binding to wrapper content).** The nonce/marker gate (`e2_verify_test_bundle_provenance`, unchanged: a harness-generated nonce written into `.e2-owner-marker`, matched via the `read` builtin before any tool candidate is inspected) is now joined by a genuine content-integrity check, `e2_verify_test_bundle_wrapper_content`. The harness (`buildE2TestToolBundle`) additionally writes a manifest file (`.e2-owner-manifest`) recording, for each of the seven bundle tools, the exact bytes of the wrapper shim it just wrote, hex-encoded. Every time a tool is resolved through the bundle (`e2_resolve_test_bundle_tool`), the script re-reads that wrapper's *current* on-disk bytes and compares them, exactly, against the manifest's recorded entry for that basename — immediately before the candidate is trusted, on every resolution, not once at bundle-open time. Reusing a nonce/marker in a directory without a matching manifest, forging a manifest that does not describe the directory's real wrapper bytes, or editing a wrapper's content or exec target after the bundle was built all now fail at this real content comparison. **What this does not prove, and the Retry-4 correction:** it is a plain byte-equality check, not a cryptographic signature. Through Retry-3, this meant it could not stop an entity that fully controls the bundle directory *and* can also freely rewrite the manifest and nonce/marker to match its own wrapper content from constructing a self-consistent forged bundle — Codex's Retry-3 review (`R5R3-F1-BUNDLE-INTEGRITY`) confirmed exactly this: the negative tests at that revision exercised only directories that did *not* attempt full self-consistency (an unrelated/reused directory, a manifest that does not match, or a wrapper edited after the fact). **As of Remediation-5 Retry-4, the trust root is no longer solely the caller-controlled directory/nonce/marker/manifest/wrapper-byte set.** `e2_verify_test_bundle_provenance` also requires a fixed `E2_TEST_BUNDLE_CAPABILITY` constant — always empty in this checked-in file, never read from the environment or any bundle-directory file — to be non-empty and equal the supplied nonce; only a private, harness-minted temporary *copy* of this script (`ops-tests/helpers/runE2Script.ts: buildE2TestToolBundle`/`buildCapabilityScriptCopy`) ever carries a non-empty value there, substituted in at copy-creation time from a token generated fresh in Node memory. A test (or any other caller) that assembles a fully self-consistent forged bundle — its own directory, its own nonce, real executable wrappers for all seven basenames, and a manifest whose recorded hex genuinely matches them — still runs the checked-in file when it does not go through that harness function, and the checked-in file's capability constant is always empty, so provenance now fails closed regardless of self-consistency. This is proven directly by a new spec case in `R5R2-M1 bundle content-integrity` (`R5R4-F1`). The bundle continues to carry no uid==0/production-root trust claim and remains reachable only through the internal `e2_lookup_use_test_bundle` flag no environment variable can set — see the unchanged production-non-reachability description immediately below. This capability-copy mechanism also closes a latent structural gap, not just a test-quality one: previously, "the bundle is unreachable in production" rested entirely on the deployment assumption that production invocations never carry the approved test-control env vars; now the checked-in production file structurally cannot activate the bundle from those env vars alone, regardless of that assumption.

`e2_resolve_test_bundle_tool` resolves against this directory with the same fixed-basename/no-symlink-component/executable checks every tool gets, but deliberately *without* the uid==0/mode-attestation chain (`e2_resolve_attested_candidate`) production tools require: that chain is a claim about *system* trust, meaningless for a directory the test process itself just created and will remove, and this resolver is reachable *only* when the harness explicitly opts in (an internal `e2_lookup_use_test_bundle` flag, never read from any environment variable, set only by this one dispatch block) — it can never affect real production dispatch (Linux/Darwin calling `run_e2_lookup` directly), never resolves `gcloud` (the token owner's test branch never calls it), never accepts the production origin (the seam's own gate already refuses that), and duplicates no validator/parser/mapping logic — `run_e2_lookup`, `e2_validate_document_body`, `e2_check_host_allowlist`, and the output/deletion path are all reused completely unmodified. Without a bundle directory, an `ELIGIBLE` fixture still fails closed with `tool_resolution_failed` at `run_e2_lookup`'s own tool resolution — identical terminal behavior to before this remediation, just reached one level deeper. This is Windows-host **test evidence only**: it does not make Windows a production or POSIX-evidence-passing host (see the Windows-outcomes paragraph below), and it never accepts a non-loopback origin.

**Split RC-4 seams (D1-F3); classify-only now requires the exact literal `1` (Remediation-5, R4-F6).** The single classify-then-fall-through-to-lookup fixture is two structurally separate seams. The **pure classifier seam** (`E2_TEST_MODE=1` + `E2_TEST_DIAGNOSTICS=1` + `E2_TEST_CLASSIFY_ONLY=1` + `E2_TEST_HOST_FACTS_V1`) shares the identical `classify_wsl`/`classify_filesystem_lines` logic production uses, but only ever prints one closed classification token (`ELIGIBLE`, `NOT_RUN_WSL1_UNSUPPORTED`, or a `NOT_RUN_FILESYSTEM_TYPE_*` token) and exits — it never acquires a token, never resolves `gcloud`/`node`, never creates a temp lookup body or a socket, and never emits a `RESULT`/`REASON` line, even when the verdict is eligible. This seam is fully pure Bash (Remediation-4, R3-F1): base64 decoding and `/proc/version`-shaped text bounding for the fixture use pure-Bash builtins (`e2_pure_b64_decode_or_dash`, `e2_pure_bound_text`) instead of the `base64`/`mktemp`/`head`/`grep` binaries production's real host-facts reading still legitimately uses, and it is dispatched at the top level *before* the production platform/tool resolver — it resolves zero external tools and is therefore genuinely reachable and substantive on any host, including one with an empty root table. **As of Remediation-5, the recognition check is exact-value, not nonempty; as of Remediation-5 Retry-2, non-qualifying-but-present values are also a typed closed rejection, not a silent fallthrough:** Remediation-4 activated classifier-only mode on *any* nonempty `E2_TEST_CLASSIFY_ONLY` (including `"0"` or arbitrary text), broader than the documented `=1` contract; Remediation-5 narrowed activation to the exact literal `1`, but a present, non-`1` value (`"0"`, whitespace, arbitrary text) still fell through to the host-independent lookup seam and reached token/lookup handling — Codex's Retry-3 review (R5R1-F2) flagged this as an unclosed fallthrough. Remediation-5 Retry-2 adds an explicit closed grammar checked before both the classify-only dispatch and the lookup seam: unset or empty is "not classifier-only" (unaffected, falls through to the lookup seam exactly as before); the exact literal `1` activates classifier-only mode; any other present, nonempty value now dies `E2_ERROR invalid_mode` (exit 2) before any loopback/token/tool/network work — zero stub requests, zero token acquisition. **As of Remediation-5 Retry-3, this zero-side-effect claim is proven jointly, not separately, for each of the three closed invalid shapes (`"0"`, arbitrary text, whitespace):** `ops-tests/e2-shift-close-document-lookup.spec.ts`'s `R5R2-F2 exact classifier control` block runs each shape through a real poisoned-`gcloud` PATH (proving zero tool/poison invocation, not merely zero network) with `E2_TEST_EXPOSE_STATE=1` (proving zero `test_body_created` marker) alongside the pre-existing zero-stub-request and typed-`invalid_mode`/exit-2/no-`RESULT` assertions — closing the gap Codex's Retry-2 review found where only request-count and the typed error were jointly proven. The **lookup seam** (reached without a qualifying `E2_TEST_CLASSIFY_ONLY`) requires all four of test mode, diagnostics, an exact loopback origin with a syntactically valid port, and a non-empty `E2_TEST_TOKEN` — checked by the seam itself, before it even parses the fixture — and only then classifies and, on an eligible verdict, falls through to the real `run_e2_lookup`. This replaces Remediation-1's downstream-only enforcement (host/token were previously checked inside `run_e2_lookup` after the fixture had already been classified), which Codex's diagnostic review flagged as not the selected exact four-condition pre-lookup gate.

**`reap_child_once` `errexit` fix (Remediation-5, disclosed follow-up, not one of the nine Remediation-4 findings).** `wait "$child_pid"` propagates the reaped direct child's own exit/signal status as `wait`'s own return value; under `set -euo pipefail`, a bare `wait` call returning nonzero is itself a "failing command" and previously aborted the whole script at that line — before `run_e2_lookup`'s own curl-failure branch could ever run and emit `RESULT INACCESSIBLE` / `REASON transport_failure`. This was unreachable, and so undetected, on this Windows/Git-Bash host prior to Remediation-5 (a real curl connection failure was never reached here before the host-independent loopback seam existed); it is now fixed with the same `cmd || rc=$?` capture idiom Remediation-4's R3-F11 already established for token-status capture in this same file. This is a genuine correctness fix to existing (not newly authored) script behavior, disclosed here because Remediation-5's own R4-F1 change is what first made it observable — it was not previously known or claimed fixed.

**Pure trust-facts evaluator now fully pure Bash (Remediation-4, R3-F1).** `--evaluate-trust-facts-v1` used to still resolve `mktemp`/`head`/`grep`/`xxd`/`iconv`/`cat` to parse the stdin protocol, so it was structurally unreachable behind the shared production bootstrap on any host with an empty root table. It now reads all of stdin via the `read -r -d ''` Bash builtin, hex-decodes and UTF-8-validates path fields via new pure-Bash helpers (`e2_pure_hex_decode_utf8`, `e2_pure_hex_decode_raw` — arithmetic hex-literal expansion plus `printf '%b'`, no external process), and is dispatched before the production resolver. It resolves no external tool, acquires no token, opens no socket, and emits no production `RESULT` on any host — and now reaches real `POLICY_ACCEPT`/`POLICY_REJECT`/`POLICY_NOT_RUN`/`INPUT_REJECT` verdicts on this Windows/Git-Bash development host too, not just a generic resolver failure.

**Token-acquisition return-code capture fixed (Remediation-4, R3-F11).** `tok=$(cmd) || true` followed by reading `$?` always read `0` — the `|| true` made the compound statement itself always succeed, so the real `gcloud`/token-resolution exit status was unconditionally discarded, and a resolver failure could misreport as `token_acquisition_failed` instead of `tool_resolution_failed`. All three sites (`e2_get_access_token_production`, `e2_get_access_token`, `run_e2_lookup`'s token capture) now use `cmd || rc=$?` (with `rc=0` initialized beforehand): `set -e` is still satisfied by the compound statement as a whole, but `$?` inside the `||` branch correctly captures the real failing exit status before it is overwritten. Empty-token output is also now explicitly rejected even when the captured exit status was somehow `0`, and no curl/network call is reachable after a token failure of any kind.

**Complete G1 trust predicate + live production trust anchor (RC-2).** As of Remediation-4 the evaluator's own per-field predicate logic is pure Bash and substantively exercised on any host (see above); the *live* trust-anchor verification below remains a real-Linux/Darwin-only production concern. The G1 evaluator's canonical accept profile requires exactly the five fixed paths (`/`, `/usr`, `/usr/bin`, `/usr/bin/stat`, `/usr/bin/od`) with correct uid (0), non-group/world-writable mode, correct kind/fileType, and (for the two executables) a non-empty tool-version token and the executable bit set; a missing member, an unexpected sixth (non-canonical) path, or any mismatched fact forces `POLICY_REJECT`, not a silent pass. Real (non-fixture) production dispatch on Linux/Darwin now live-verifies this same canonical set via the fixed-root-resolved, self-attesting `stat` chain described above (stat attests itself first, then `/`, `/usr`, `/usr/bin`, `/usr/bin/od`) before trusting `uname`/`findmnt`/`mount`; a failed trust anchor is `tool_resolution_failed` (exit 4), not a silent proceed.

**Filesystem/POSIX-owner set (RC-5), unchanged.** Exactly six Linux-accepted types (`ext2`/`ext3`/`ext4`/`xfs`/`btrfs`/`f2fs`), two Darwin-accepted types (`apfs`/`hfs`), and ten always-rejected types (`9p`/`drvfs`/`cifs`/`smbfs`/`ntfs`/`ntfs3`/`fuseblk`/`vfat`/`msdos`/`exfat`); `overlay`/`tmpfs` are a conditional non-pass. `findmnt`/`mount`/`stat` are invoked only through the resolver's canonical variables, only after bootstrap.

**Windows outcomes — pure modes AND the host-independent loopback seam now substantively PASS/REJECT; the real production resolver/trust-anchor chain remains `NOT_RUN`, never `PASS` (Remediation-5 supersedes the Remediation-4 paragraph below its own line).** This script was implemented and locally verified on a Windows/Git-Bash development host, whose `$OSTYPE` (`cygwin`) selects the empty "Other" root table (see above), and whose real coreutils are not uid-0-owned in this stat dialect's terms — so the **production trust-anchor/tool-resolver chain** (the uid==0-attested `stat`/canonicalizer/`curl`/`node`/etc. resolved from a real platform root table) remains genuinely unreachable here: real production dispatch, WSL/filesystem classification exercised through *that* path specifically, and the real-POSIX-only signal-delivery rows all still fail closed with `tool_resolution_failed` or assert `NOT_RUN_SIGNAL_SEMANTICS_UNAVAILABLE`, and still require an actual Linux or Darwin host. This is the deliberate, accepted consequence of closing R2-F2 (OSTYPE-gated platform selection before any external tool) and R2-F3 (uid==0 attestation on every retained tool) together.

As of Remediation-4 (R3-F1/R3-F2), the pure evaluator and pure classifier seams were already outside that ceiling (fully pure Bash, zero external tools). **As of Remediation-5 (R4-F1), the host-independent diagnostics loopback seam joins them**: a non-`ELIGIBLE` classification (WSL1/WSL2-with-rejected-filesystem/unrecognized-filesystem/etc.) now reaches its real token directly, and an `ELIGIBLE` classification completes a real HTTP round trip — exact status-code mapping (200/malformed/wrong-name/404/400/401/403/429/5xx/connection-refused), the real RC-8 JSON body validator, the real exact field masks, and real body-deletion/privacy containment — through the sanitizer-owned test tool bundle described above. None of this makes Windows a production or POSIX-evidence-passing host: the test tool bundle carries no uid==0/production-root trust claim, is reachable only through an internal flag no environment variable can set, and the seam's own gate still refuses the production origin outright. `ops-tests/e2-shift-close-document-lookup.spec.ts` reports genuine PASS/REJECT/typed-failure assertions for all of this, distinct from the legitimate `E2_ERROR tool_resolution_failed`/exit-4 `NOT_RUN` still asserted wherever the real production resolver chain specifically is what's under test (an `ELIGIBLE` fixture with no test tool bundle, `E2_TEST_MANIFEST_DIAG` diagnostics, and the two signal-model rows that deliberately omit the bundle) — `NOT_RUN` is never counted as `PASS` in any category. The two signal-delivery-dependent test rows that used to be guarded only by Windows' fake-uid mapping still assert `NOT_RUN_SIGNAL_SEMANTICS_UNAVAILABLE` for the platform-level reason documented previously (Node's `child_process.kill()` cannot deliver a real POSIX signal to a non-Node child on Windows). **Decoder fork-cost gap closed (Remediation-5 Retry-2, R5R1-F3 — supersedes the 300-byte-substitute description previously here).** The pure classifier's base64 decode (`e2_pure_b64_decode_or_dash`) previously forked one subshell per decoded byte (`esc+=$(printf ...)`), measuring roughly 15-17ms/byte on this host — a genuine ~4096-byte `/proc/version`-shaped boundary fixture took close to a minute of wall time, so the exact `T-POSIX-PROC-4096`/`4097` byte boundary was exercised at a smaller (300-byte), still-substantive-but-not-boundary-exact payload instead. The per-byte hex-escape append now uses `printf -v` (a Bash builtin, no fork), making the same 4096/4097-byte payload decode in well under a second; `T-POSIX-PROC-4096` and `T-POSIX-PROC-4097` now exercise the real byte-exact boundary at full size, made distinguishable via a diagnostics-only `test_proc_version_bound_rc` marker (every fixture in that describe block shares an identical final `NOT_RUN_FILESYSTEM_TYPE_UNAVAILABLE` classification token regardless of the bound's own accept/reject verdict, so the marker — not the final token — is what the boundary tests assert). Fixing this also surfaced and closed a real off-by-one in `e2_pure_bound_text`: the bound previously checked the raw (pre-LF-strip) decoded length against `<= 4097` — one byte too permissive relative to `e2_read_proc_version_bounded`'s own `size -ge 4097 -> reject` file-read bound — and checked it before, not after, the optional trailing-LF strip, so a 4097-byte payload whose only excess byte was a trailing LF was wrongly accepted; the bound is now `<= 4096` applied to the raw length, matching the real file-reader exactly, with or without a trailing LF. A separate bug in the same area — `$( )` command substitution silently strips all trailing newlines from whatever it captures — was masking this: `e2_classify_host_facts` now appends a non-newline sentinel byte before each decode capture and strips exactly that sentinel back off, so a decoded payload's own trailing LF(s) are never lost before the bound ever sees them. **NUL/control contract closed (Remediation-5 Retry-3).** Codex's Retry-2 review found the decoder's NUL contract untested and, on inspection, unsound: `e2_pure_b64_decode_or_dash` reconstructs its result as a Bash string, which cannot represent an embedded NUL byte (0x00) — appending one would have silently truncated the decoded output at that byte, turning invalid input into a different, shorter accepted string with no signal to the caller. The decoder now detects a decoded NUL byte-by-byte, during decoding, and rejects it (returns 1) before any byte reaches the final string reconstruction — a NUL-bearing kernel-release or filesystem-lines fixture now dies the existing typed `internal_parser_error` (exit 5); a NUL-bearing proc-version fixture reaches the existing, pre-established degrade-to-empty-proc_version behavior (documented above), now made observable via a new diagnostics-only `test_proc_version_decode_rc` marker distinguishing "decode failed" from "decode succeeded, bound rejected." `ops-tests/e2-shift-close-document-lookup.spec.ts`'s `T-POSIX-PROC-*` block tests both shapes with a genuine embedded NUL byte, not ordinary text. Fixing this also surfaced a second, independent latent defect discovered while building the Retry-3 bundle content-integrity check below: the *existing* `esc+=$(printf '\\x%02x' ...)` per-byte subshell construction (shared by `e2_pure_hex_decode_utf8` and `e2_pure_hex_decode_raw`) silently dropped a trailing 0x0a byte from the reconstructed string on this host's Bash/printf build whenever that byte was the final loop iteration's own command-substitution capture — invisible at the short string lengths (well under a UUID/path) those two functions had previously ever been exercised with, and reachable in practice only once the Retry-3 manifest-content comparison exercised them at real wrapper-shim length (dozens of bytes). Both functions are rebuilt on the same non-subshell `printf -v` pattern the base64 decoder's own per-byte loop already used, closing that specific subshell-per-byte defect at its root rather than working around it at each call site. **This did not, however, close a separate, distinct defect Codex's Retry-3 review found in the same area (`R5R3-F3-DECODER`): ordinary callers of both functions still captured their output via unguarded `$(...)` command substitution, which strips a trailing newline regardless of what the decoder itself preserves internally — so a caller-supplied hex payload decoding to, e.g., `/usr\n` or `directory\n` could still silently collapse to the accepted literal `/usr`/`directory` at the call site. As of Remediation-5 Retry-4, both ordinary call sites (`decoded_path` in the trust-facts evaluator, `ft_decoded` in the canonical-fileType check) use the same sentinel-preserving capture guard the manifest wrapper-content comparison already used, closing this at the caller boundary.** **Real coverage of the production resolver, trust anchor, canonicalizer, running-Bash identity check, and WSL/filesystem classification via the real production path still requires an actual Linux or Darwin host — this remains a separately authorized, not-yet-run operational gate, not evidence of production readiness.**

Do not run this script's no-argument production mode against the real Firestore endpoint without that separate authorization.
